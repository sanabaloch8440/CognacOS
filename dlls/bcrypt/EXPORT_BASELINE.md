# bcrypt.dll Windows 11 x64 export baseline

Source: [learn-more/winexports](https://github.com/learn-more/winexports/tree/master/data/exports/nt100_x64_26200), binary metadata version **10.0.26100.7623**, AMD64. The inventory records the exact 60 named exports and ordinals from that reference binary. It is pinned to this servicing build and should be refreshed only against a newly inspected reference image.

CognacOS currently has 54 implemented export entry points in its build-time implementation allowlist: BCryptOpenAlgorithmProvider, BCryptCloseAlgorithmProvider, BCryptGetProperty, BCryptCreateHash, BCryptHashData, BCryptFinishHash, BCryptDestroyHash, BCryptDuplicateHash, BCryptHash, BCryptGenRandom, BCryptDeriveKeyPBKDF2, BCryptGetFipsAlgorithmMode, BCryptEnumAlgorithms, BCryptEnumProviders, BCryptFreeBuffer, BCryptSetProperty, BCryptGenerateSymmetricKey, BCryptEncrypt, BCryptDecrypt, BCryptDestroyKey, BCryptDuplicateKey, BCryptImportKey, BCryptExportKey, BCryptCreateMultiHash, BCryptProcessMultiOperations, BCryptKeyDerivation, BCryptDestroySecret, BCryptDeriveKey, BCryptImportKeyPair, and BCryptVerifySignature. The four remaining exports are present in the PE export table with ABI-shaped fail-closed entry points: ML-KEM encapsulation/decapsulation, Diffie-Hellman secret agreement, and the auditing interface. They return STATUS_NOT_SUPPORTED because the corresponding cryptographic/key-blob or platform audit backend is not yet implemented. Implemented APIs have feature limitations, so this count does not imply complete Windows behavioral compatibility.

The one-shot `BCryptHash` path shares the SHA-2/HMAC provider selection and checks the output capacity before writing. `BCryptDuplicateHash` copies the complete incremental state and independently zeroizes its copied secret when destroyed. Both accept either library-managed storage (null pointer with zero length) or a caller-supplied object buffer (non-null pointer with nonzero length). The Rust/AWS-LC hash state itself remains in the internal handle table; the caller buffer is currently ABI-accepted but not used as the cryptographic state.

Known limitations: AES is a deliberately bounded subset (AES-128/192/256 CBC with PKCS#7-style block padding and GCM with 1–16-byte nonces and all Microsoft Primitive Provider tag sizes from 96 through 128 bits (12-byte nonces remain recommended)). AES defaults to CBC, chaining mode can be changed on provider or key handles, and GCM exposes the Windows `AuthTagLength` range of 12–16 bytes in one-byte increments; other cipher families and modes are not implemented. Private-key generation/import and signing, advanced algorithm/context configuration, configurable FIPS policy, provider registration, secure key storage, pseudo-handles, and full Windows CNG caller-owned object-buffer storage semantics remain incomplete: caller buffers are accepted and validated, but backend state remains internally allocated. Handles are process-local heap objects; robust invalid/stale handle validation and cross-process provider semantics remain future work. Do not treat this as a complete bcrypt.dll replacement.


Multi-hash support: providers opened with `BCRYPT_MULTI_FLAG` can create up to 4096 independent SHA-256/SHA-384/SHA-512 or HMAC states using `BCryptCreateMultiHash`. `BCryptProcessMultiOperations` accepts the documented `BCRYPT_MULTI_HASH_OPERATION` records and executes hash-data/finalize commands in caller order. Multi-hash states are reusable after finalization, matching the multi-operation workflow. The implementation uses sequential AWS-LC operations rather than SIMD parallel hashing, does not accept caller-owned object storage, and currently requires the documented provider flag. The batch is prevalidated and all per-hash capacity is reserved before state mutation, so allocation failure cannot leave a partially applied batch.


PBKDF2 key derivation: `BCryptOpenAlgorithmProvider(L"PBKDF2")` creates the KDF provider, `BCryptGenerateSymmetricKey` captures bounded password/input-key material in a zeroizing opaque handle, and `BCryptKeyDerivation` parses the Windows `BCryptBufferDesc` parameters (`KDF_HASH_ALGORITHM`, `KDF_SALT`/`KDF_GENERIC_PARAMETER`, optional `KDF_ITERATION_COUNT`) and derives SHA-256/384/512 PBKDF2 output. Iterations are bounded to 10,000,000 and input/salt to 1 MiB. HKDF, SP800-108, TLS PRF, secret-agreement KDFs, and caller-owned key object buffers remain unsupported.


Additional CNG operations: `BCryptDeriveKey` supports the `TRUNCATE` raw-secret KDF for CognacOS opaque secret handles; `BCryptDestroySecret` releases and zeroizes those handles. RSA support currently imports bounded `BCRYPT_RSAPUBLIC_BLOB` public keys and verifies precomputed SHA-256 digests with PKCS#1 v1.5 padding. RSA private-key generation/import and signing, OAEP/PSS paddings, and full Windows key-object semantics remain unsupported. Public-key verification supports SHA-256, SHA-384, and SHA-512 with the Windows PKCS#1 padding-info structure. These are bounded subsets, not complete implementations of the corresponding Windows APIs.


## x64 ABI corrections and regression coverage

The provider enumeration ABI now matches the Windows declarations: `BCRYPT_PROVIDER_NAME` contains only its `LPWSTR pszProviderName` field (8 bytes on x64), rather than an extra flags field. `BCRYPT_ALGORITHM_IDENTIFIER` is asserted to be 16 bytes on x64; the authenticated-cipher info, buffer descriptor, multi-hash operation, and RSA blob header also have compile-time x64 size guards. Runtime tests verify the same layouts.

The `BCryptGenRandom`, `BCryptGetFipsAlgorithmMode`, and `BCryptFreeBuffer` entry points now have unmangled export symbols. The PBKDF2 direct-call ABI uses the Windows `ULONGLONG` iteration-count parameter (with the current crypto backend limiting executable counts to `u32::MAX`). The RNG provider can be opened as `RNG` using the Microsoft Primitive Provider name, queried for `AlgorithmName`, and passed to `BCryptGenRandom` with flags zero. A null algorithm handle continues to require `BCRYPT_USE_SYSTEM_PREFERRED_RNG`.

`BCryptEnumAlgorithms` now uses the Windows operation-bit mask and interface-class values for the implemented AES, SHA-2, RSA, RNG, and PBKDF2 providers, including `BCRYPT_KEY_DERIVATION_OPERATION` / interface 7. It no longer misreports PBKDF2 as a secret-agreement algorithm, and returns a null list for a valid operation mask with no matching algorithms. `BCryptEnumProviders` now accepts the required algorithm identifier as its first argument, validates provider support for that algorithm, and emits the corrected one-pointer provider record. Its advertised provider name is `Microsoft Primitive Provider`, matching the provider alias accepted by `BCryptOpenAlgorithmProvider`.

These checks improve ABI fidelity but do not establish complete CNG compatibility. The Windows x64 build step verifies the PE32+ image and all 60 export names; behavior still needs differential testing against Windows for each supported API and error path.


PBKDF2 accepts an empty password as well as non-empty password material. Its `BCryptKeyDerivation` path accepts the documented optional salt and iteration parameters, including the empty-salt/10,000-iteration defaults. PBKDF2-derived key handles can be duplicated with `BCryptDuplicateKey` and released through `BCryptDestroyKey`; the key material is zeroized when the final handle is removed. RSA public-key handles expose `AlgorithmName`, `KeyLength`, and `PublicKeyLength` through `BCryptGetProperty`, and can be duplicated.


Hash finalization now follows CNG lifecycle rules: ordinary hash handles become unusable after `BCryptFinishHash`, while providers opened with `BCRYPT_HASH_REUSABLE_FLAG` can create reusable hash objects that reset after each successful finish. Fixed-size hash output lengths must match the digest size exactly. The flag is accepted only for hash providers.


## Additional implementation batch

RSA and RSA_SIGN are recognized as distinct Windows algorithm identifiers. RSA signing is enumerated under the signature interface (class 5), separately from RSA asymmetric encryption (class 3). RSA now supports Windows-style unfinalized key-pair creation, explicit `BCryptFinalizeKeyPair`, and SHA-256/384/512 PKCS#1 v1.5 prehash signing. Signing rejects unfinalized handles, supports the documented size-query call (`pbOutput == NULL`), and can be verified with the corresponding public key. RSA key generation uses the OS-backed random source exposed by the Rust `rand` crate; private keys are held in opaque process-local handles. RSA PSS signing, private-key blob import/export, and full CNG key-object storage are still not implemented.

`BCryptDeriveKeyCapi` is implemented for SHA-2 hash handles, including the legacy two-block ipad/opad expansion for outputs larger than one digest. It does not yet reproduce every legacy CryptoAPI target-algorithm and salt option, so callers requiring exact CAPI interop must still be tested against Windows.

The local CNG configuration API now has process-local context create/delete/configure/query, function add/remove/configure/enumerate, provider add/remove/enumerate, and function-property set/query operations. The local configuration table is supported; domain configuration returns `STATUS_NOT_SUPPORTED`. The store is volatile and does not write the Windows registry or provide cross-process synchronization.

Configuration-change notification APIs now create manual-reset Windows event handles, register them in a synchronized process-local subscriber set, signal them after successful local provider/context mutations, and close them on unregister. The non-Windows test implementation uses opaque synthetic handles to exercise registration lifecycle without pretending to create OS events. Four exports remain fail-closed: ML-KEM encapsulation/decapsulation, Diffie-Hellman secret agreement, and the platform auditing interface.


Provider registration now supports the local process-level provider-name registry, provider enumeration, provider lookup, and resolution records. Provider registration metadata is currently represented by empty user/kernel image descriptors; it is not persisted to the Windows registry and does not load arbitrary provider DLLs. Context configuration and provider registration are therefore compatibility scaffolding for CognacOS rather than a drop-in replacement for Windows machine-wide CNG configuration.
