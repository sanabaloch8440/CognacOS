# bcrypt.dll Windows 11 x64 export baseline

Source: [learn-more/winexports](https://github.com/learn-more/winexports/tree/master/data/exports/nt100_x64_26200), binary metadata version **10.0.26100.7623**, AMD64. The inventory records the exact 60 named exports and ordinals from that reference binary. It is pinned to this servicing build and should be refreshed only against a newly inspected reference image.

CognacOS currently has 20 implemented export entry points in its build-time implementation allowlist: BCryptOpenAlgorithmProvider, BCryptCloseAlgorithmProvider, BCryptGetProperty, BCryptCreateHash, BCryptHashData, BCryptFinishHash, BCryptDestroyHash, BCryptDuplicateHash, BCryptHash, BCryptGenRandom, BCryptDeriveKeyPBKDF2, BCryptGetFipsAlgorithmMode, BCryptEnumAlgorithms, BCryptEnumProviders, BCryptFreeBuffer, BCryptSetProperty, BCryptGenerateSymmetricKey, BCryptEncrypt, BCryptDecrypt, and BCryptDestroyKey. The remaining 40 exports are present in the PE export table but fail closed with STATUS_NOT_IMPLEMENTED; they are not behaviorally compatible yet. Implemented APIs have feature limitations, so this count does not imply complete Windows behavioral compatibility.

The one-shot `BCryptHash` path shares the SHA-2/HMAC provider selection and checks the output capacity before writing. `BCryptDuplicateHash` copies the complete incremental state and independently zeroizes its copied secret when destroyed. Both currently require library-managed object storage; caller-supplied hash-object buffers remain unsupported.

Known limitations in this first batch: AES and other cipher providers, symmetric/asymmetric key lifecycle, signing/verification, multi-hash, algorithm enumeration/configuration, FIPS policy, provider registration, secure key storage, and full Windows CNG object-buffer semantics are not implemented. Handles are process-local heap objects; robust invalid/stale handle validation and cross-process provider semantics remain future work. Do not treat this as a complete bcrypt.dll replacement.
